# MX-Desktop-Sharing-NEXT

LiveKit ベースのデスクトップ共有。設計の核は **ルームごとに 1 ノード、人ごとに 1 配信 URL**。

- **ルームは LiveKit ノードに紐づく。** 作成時にどの LiveKit 認証情報を使うか指定し、そのルームのメディアトラフィックと無料枠はそのノードで消費されます。
- **一般ユーザーは自分のノードを持ち込む。** 各自が自分の LiveKit Cloud project を接続し、自分の枠を使うので誰とも取り合いになりません。
- **受け皿としての内蔵ノード。** 管理者は任意のノードを「内蔵」に昇格させてサイト全体で共有できます。一般ユーザーに開放するかの切り替えと、ルーム数の上限もあります。
- **認可はプロトコル層で行う。** メンバー表にいない → トークンが出ない → ルームに繋がらない → どのトラックも購読できない。フロント側のフィルタではありません。
- **OBS は WHIP 直通。** `enableTranscoding: false` なので、月 60 分のトランスコード枠を一切消費しません。
- **「OBS 配信」は本物のスイッチ。** オーナーはこのルームの WHIP 入口をワンクリックで閉じられます。配信中のものは即座に切れ、すでに配った配信 URL はすべて無効になります。ブラウザ共有は別経路なので影響しません。
- **環境変数 2 つで動く。** 管理者アカウントは自動作成、暗号鍵は自動供給、LiveKit は Web 画面で設定します。

このサイトを Vercel にデプロイする方法は [DEPLOY.md](DEPLOY.md) を参照。

## クイックスタート

必要な環境変数は 2 つだけです。`.env.example` を `.env.local` にコピーし（Next は `.env.example`
自体を**読みません**。あのファイルを編集しても効果はありません）、この 2 つを埋めます:

```bash
DATABASE_URL=postgresql://...@ep-xxx-pooler.../neondb?sslmode=require
ADMIN_PASSWORD=自分のパスワードに変更
```

**引用符は省略できます** —— あってもなくても解析結果は同じです。唯一の例外は値に `#` を含む場合で、
引用符なしだとコメントとして黙って切り捨てられるので、そのときは付けてください。`ADMIN_PASSWORD` は
空にできません。`""` のままは未設定と同じで、管理者アカウントは作成されません。

続いてテーブルを作成し、起動します:

```bash
npm install
npm run db:migrate
npm run dev
```

`db:migrate` は `drizzle/` 配下のマイグレーションファイルを読んで 12 個のテーブルを作ります。
アプリと同じ env ファイルを読みます（`.env.local` が `.env` より優先）。**Vercel へのデプロイでは
手動で実行する必要はありません** —— マイグレーションはすでにビルドに組み込まれているので、
`DATABASE_URL` を設定してコードを push するだけです。詳細は [DEPLOY.md](DEPLOY.md)。

`http://localhost:3000` を開き、`admin@localhost` と上のパスワードでログインしてください ——
**管理者アカウントは初回起動時に自動作成され、インストーラーはありません**。

ログインしたらサイドバーの「LiveKit ノード」→「ノードを接続」で LiveKit ノードを設定します
（認証情報の取得方法は次節）。LiveKit は環境変数を一切使いません。

その他のコマンド: `npm test`（137 項目）、`npm run typecheck`、`npm run build`。
`build` は先にデータベースのマイグレーションを走らせます（`DATABASE_URL` 未設定ならスキップ）。
データベースに触らずコンパイルだけしたい場合は `npm run build:only`。

### ログインでエラーが出る？

**まず `/api/health` を開いてください** —— 各段階の状態を項目ごとに報告します。ログイン不要で、
エラーメッセージから推測するよりずっと速いです。

```bash
curl -s http://localhost:3000/api/health | python -m json.tool
```

5 項目の順番: `DATABASE_URL` が設定されているか → データベースに繋がるか →
**12 個のテーブルが作られているか** → `ADMIN_PASSWORD` が設定されているか → 起動時の初期化が通ったか。
前の項目が通っていないと後ろはスキップされるので、常にいちばん上の赤い項目だけを直せば済みます。

ログイン API は原因ごとにステータスコードを分けています:

| レスポンス | 意味 |
| --- | --- |
| `503 not_configured` | データベースに繋がらない、テーブルがない、または `DATABASE_URL` 未設定 |
| `503 admin_not_configured` | データベースは通じているが `ADMIN_PASSWORD` が空で、管理者アカウントが作られていない |
| `401 invalid_credentials` | アカウントはあるがパスワードが違う |
| `429 rate_limited` | 同じメールアドレスで 15 分以内に 8 回失敗（同一 IP なら 30 回） |

最も誤解しやすいのは **テーブルが作られていない** ケースです。症状は `database` が「接続できています」
と出るのにテーブルに触る API が全部落ちること —— 接続と作成は別の話だからです。`/api/health` の
`tables` 項目が、足りないテーブル名をそのまま列挙します。デプロイ時はビルドが自動で作ります。
ローカルでは `npm run db:migrate` で追いつけます。

`db:migrate` を実行したのにテーブルができない？ `drizzle/meta/_journal.json` があるか確認してください。
drizzle-kit はそれを見つけられないとき**エラーを出さず**、黙って空のものを作って何もしません。
`tests/migrations.test.mts` がまさにこれを守っています。実際に踏んでしまったら、`npm run db:push` で
マイグレーションファイルを迂回し、`schema.ts` から直接テーブルを作れます。

### 身内だけで使う（新規登録を閉じる）

**管理 →「サイト設定」→「新規登録を許可」をオフ。** このスイッチは `app_config` テーブル（キーは
`registration_enabled`）にあり、環境変数を使わず、再デプロイなしで即時反映されます。キーが無いときの
既定は**開放** —— 既存のデプロイをアップグレードしても、いきなり誰かを締め出すことはありません。

肝心なのは **アカウント作成の経路が 3 つあり、1 つ閉じるなら 3 つとも閉じないと意味がない** ことです:

| 入口 | 閉じた後の挙動 |
| --- | --- |
| メール + パスワード | `POST /api/auth/register` がそのまま `403 registration_closed` を返す |
| GitHub / Google | すでに紐づいたアカウントは通常どおりログイン。紐づいておらず、このサイトにそのアドレスも無い人はアカウント作成の段で拒否 |
| メール確認コード | 同様 —— 既存アカウントは通常どおりログイン、新しいアドレスではもうアカウントを作らない |

そのため判定は 3 つの route の入口には書かれておらず、`src/lib/site-settings.ts` の
`assertRegistrationOpen()` にまとめられ、**実際に users へ insert する 2 か所**から呼ばれます
（`src/lib/accounts.ts` の 2 つの resolve 関数と register ルート）。外部ログインと確認コードログインは
本質的に「アカウントがあればログイン、なければ作る」なので、止めるべきは後半だけで、前半は通し続けなければ
なりません。

意図的な 2 つの配置の選択:

- **確認コードの経路は「検証の後」で止め、「送信の前」では止めない。** 送信 API はアドレスがデータベースに
  あるかどうかにかかわらず同じレスポンスを返します（そうでなければユーザー名簿を照会する API になってしまう）。
  その段で止めるとこの性質が壊れます。
- **register ルートでは人間確認の前で止める。** Turnstile のトークンは 1 回しか使えません。拒否されるのが
  確定しているリクエストで使い切らせると、「このサイトは新規登録を受け付けていません」と読むためだけに
  もう一度確認をやり直させることになります。

ログインページの「新規登録」タブもそれに合わせて消え、「このサイトは新規登録を受け付けていません。
既存アカウントはこれまで通りログインできます」の一文に置き換わります —— ただしそれは案内にすぎません。
フロントが受け取った `registrationEnabled` を `true` に書き換えても、サーバー側の判定は抜けられません。

# LiveKit ノードをデプロイする

このサイトはメディアサーバーを内蔵しません。すべてのルームは LiveKit ノードに紐づける必要があり、
ノードの入手経路は 2 つあります。

**結論から**: ほとんどの人は方式 1 を選ぶべきです。方式 2 は、すでにサーバーがあって、なおかつ
Ingress サービスを追加でデプロイする気がある場合にだけ見合います。

| | 方式 1 · LiveKit Cloud | 方式 2 · 自前ホスティング |
| --- | --- | --- |
| 所要時間 | 約 3 分 | 半日以上 |
| 費用 | 無料 Build プラン、カード不要 | サーバー + 回線 |
| OBS 配信（Ingress） | **そのまま使える** | **Ingress + Redis を別途デプロイ必須** |
| 枠 | 上限あり（末尾の実算を参照） | あなたの回線だけが上限 |
| ドメイン／証明書 | 不要 | 必要（CA 発行。自己署名は不可） |

## 方式 1 · LiveKit Cloud（推奨）

### 1. 登録して project を作る

[cloud.livekit.io](https://cloud.livekit.io) を開いて登録します。無料の **Build** プランはカード不要です。

project を 1 つ作ります（名前は自由）。作成すると `wss://xxx.livekit.cloud` の形の URL が得られます ——
これが後で入力する最初の値です。

### 2. API Key を作る

project 内で **Settings → Keys → 新しい API Key** を作ると、以下が得られます:

- `API Key`（`APIxxxxxxxx` のような形）
- `API Secret`

> **API Secret は一度だけ表示されます。** ダイアログを閉じると二度と見られません。先にコピーしてください。
> 失くしても致命的ではありません: LiveKit のコンソールでその key を削除して作り直し、こちらに戻って
> 「キーを差し替え」で更新すれば済みます。

### 3. このサイトに接続する

ログイン → サイドバー **「LiveKit ノード」→「ノードを接続」**、3 つの値を入力します:

| 項目 | 入力するもの |
| --- | --- |
| ノード名 | 何でも可。自分用の名前です |
| LiveKit の URL | `wss://xxx.livekit.cloud` |
| API Key | 前の手順の key |
| API Secret | 前の手順の secret |

保存を押します。**このサイトはその認証情報で実際に LiveKit API を叩いて検証し、誤った値は保存しません。**
検証は 2 つのことを行います:

- `listRooms` —— URL と認証情報が正しいかを確認。**失敗したら保存を拒否します。**
- `listIngress` —— OBS 配信 URL を作れるかを確認。**失敗しても機能を下げるだけで、止めません**
  （ルームはブラウザ共有でそのまま使えます。WHIP の URL が出せないだけです）。

結果はノードの `capabilities` に記録され、「LiveKit ノード」ページの各行に Ingress が使えるかどうかが
表示されます。いつでも「チェック」を押して再検証できます。

### 4. webhook を設定する（推奨）

設定しなくても動きます。ただしサーバー側で入退室が記録されません（フロントは映像も人数もリアルタイムで
見えます。あれは LiveKit SDK のイベント経由で、webhook に依存しないためです）。

「LiveKit ノード」ページには、**あなた自身のノードごとに固有の** webhook URL が表示されます:

```
https://あなたのサイト/api/webhooks/livekit/<nodeId>
```

これをコピーし、LiveKit コンソール → その project → **Settings → Webhooks** に貼り付けます。

> ノードごとに URL が違う理由: webhook の署名は送信側の API key/secret で作られます。複数ノード構成では、
> 検証に使う鍵を選ぶ前に *URL から* どのノードが送ってきたのかを知る必要があります。パスの `nodeId` が
> その役目です。

### 5. ルームを作って確認する

「ルーム」ページに戻り、いま接続したノードを選んでルームを作ります。入室したら:

- 「ブラウザから共有」ボタン → OBS を入れなくても配信できます
- 「OBS 配信 URL」パネル → 「配信 URL を作成」を押すと Server と Bearer Token が得られます
- 同じパネル上部の「OBS 配信」スイッチ → オーナーがオフにすると、このルームは WHIP の受け入れをやめます

## 方式 2 · 自前ホスティングの LiveKit

### ⚠️ 先にこれを読んでください。読まないと無駄になります

**自前で立てた `livekit-server` には Ingress が含まれません。** Ingress は独立したサービスで、Redis を
介して livekit-server と通信します。つまり:

- **ブラウザからの画面共有だけ** → Ingress は不要。livekit-server だけで足ります
- **OBS/WHIP での配信が欲しい** → Ingress サービス + Redis を追加でデプロイし、livekit-server 側で
  `whip_base_url` をそこに向けて設定する必要があります

このサイトは検証時に Ingress が使えないことを検出し、ルームの画面で「OBS 配信 URL は発行できません」と
はっきり伝えます。

### ローカル開発でさっと 1 つ立てる

```bash
livekit-server --dev --bind 0.0.0.0
```

インストール: macOS は `brew install livekit`、Linux は `curl -sSL https://get.livekit.io | bash`、
Windows は GitHub Releases からダウンロード。

`--dev` モードは固定の認証情報 **`devkey` / `secret`** を使い、ローカル専用です。このサイトに接続する
ときは URL に `ws://localhost:7880` を入れます（このサイトの URL 検証は自前ホスティングと社内ネット
向けに `ws://` を受け付けます）。

### 本番デプロイ

公式に設定ジェネレーターがあり、手書きより格段に楽です:

```bash
docker pull livekit/generate
docker run --rm -it -v$PWD:/output livekit/generate
```

入力したドメインに合わせてディレクトリを生成し、中に `docker-compose.yaml`、`livekit.yaml`、
`caddy.yaml`、`redis.conf`、起動スクリプトが入っています。

`livekit.yaml` の要点:

```yaml
port: 7880
log_level: info
rtc:
  tcp_port: 7881
  port_range_start: 50000
  port_range_end: 60000
  use_external_ip: true      # クラウド環境では STUN で本当のグローバル IP を発見する
redis:
  address: redis:6379        # 本番では強く推奨
keys:
  APIyourkey: your_secret_here   # 単に key: secret の対応表
turn:
  enabled: true
  domain: turn.example.com   # 証明書と一致していること
  tls_port: 443              # 前段にロードバランサーが無ければ 443
```

`keys:` は本当に対応表だけで、専用の生成コマンドはありません —— 十分にランダムな secret を自分で作ります:

```bash
openssl rand -base64 32
```

開放が必要なポート:

| ポート | プロトコル | 用途 |
| --- | --- | --- |
| 7880 | TCP | シグナリング（前段に HTTPS/TLS 終端を置く） |
| 7881 | TCP | WebRTC メディアの TCP フォールバック |
| 50000–60000 | UDP | WebRTC メディア |
| 3478 または 5349 | TCP | 内蔵 TURN over TLS（LB が無ければ 443 に） |
| 443 | UDP | 任意の TURN/UDP。厳しいファイアウォールを抜けるため |
| 6789 | TCP | 任意の Prometheus メトリクス |

踏みやすい 2 点:

- **CA 発行の証明書が必須**で、自己署名では動きません。エンドポイントは `wss://livekit.example.com`
  のような形になります。
- **Docker では host networking を使うこと。** ポートごとの bridge マッピングにすると、メディアの
  ポート範囲が壊れます。

### Ingress のデプロイ（OBS 配信が必要な場合のみ）

- 独立したサービス。**Redis のアドレスは livekit-server が使うものと同一でなければなりません**
- インスタンスあたり **4 CPU / 4 GB メモリ以上** を推奨
- ポート: RTMP `1935/TCP`、WHIP `8080/TCP`、WHIP over UDP `7885/UDP`
- 設定項目: `api_key`、`api_secret`、`ws_url`、`redis`
  （または環境変数 `LIVEKIT_API_KEY` / `LIVEKIT_API_SECRET` / `LIVEKIT_WS_URL`）
- **livekit-server 側でも `whip_base_url` を設定する必要があります**（RTMP も使うなら
  `rtmp_base_url` も追加）。設定しないとサーバーが ingress の URL を作れません
- 複数インスタンスならロードバランサーが必要: RTMP は TCP LB、WHIP は HTTP リバースプロキシ

良い知らせ: **WHIP 直通（bypass transcoding）は CPU をほとんど使いません** —— 公式の原文は
"a WHIP session with transcoding bypassed consumes minimal resources"。このサイトは既定で直通
（`enableTranscoding: false`）なので、自前 Ingress のマシンにかかる負荷は想像よりずっと小さいです。
本当に CPU を食うのは RTMP と、トランスコードを有効にした WHIP で、解像度と層数に比例して増えます。

## OBS の設定

配信 URL を得たら:

1. OBS → 設定 → 配信 → **サービスは `WHIP`**
2. **Server** = パネルの Server
3. **Bearer Token** = パネルの Bearer Token（WHIP でのストリームキーの呼び方）

URL が作れない、あるいは配信中に切られる場合は、まずパネル上部の「OBS 配信」スイッチをオーナーが
オフにしていないか確認してください。

WHIP 直通にサーバー側 simulcast はありません。画質を複数用意するには **OBS 32.1.0 以降** で自分で
有効にします（1〜4 層に対応）。

## ノード接続のよくある問題

| 症状 | 原因 / 対処 |
| --- | --- |
| URL を `https://` で入力した | 直す必要はありません。自動で `wss://` に変換し、余計なパスと末尾のスラッシュも取り除きます |
| 保存時に「接続できないか認証情報が無効」と出る | `listRooms` の探索が失敗しています。URL がその project のものか、key と secret が対になっているか、secret を全部コピーできているかを確認 |
| Ingress が「—」／利用不可 | Cloud: project で Ingress が有効になっていない、または Ingress の同時数が上限（無料層は 2 つだけ）。自前: Ingress を未デプロイ、または `whip_base_url` が未設定 |
| この認証情報はすでに接続済み | 同一ユーザー + 同一 URL + 同一 key は一度しか接続できません。一覧から既存のものを探してください |
| 急に全リクエストが失敗する | 無料枠を使い切りました。**超過は素直に失敗し、課金は一切されません** —— 翌月を待つかノードを替えてください |
| secret を失くした | LiveKit コンソールで key を作り直し、こちらに戻って「キーを差し替え」で更新（書き込む前に新しい認証情報を検証します） |

## アーキテクチャ

```
ブラウザ ──── Next.js on Vercel ──── Neon Postgres
  │          (ログイン/ルーム/メンバー/トークン署名)
  │                 │
  │ WebRTC          │ server SDK（そのルームが属するノードの認証情報で）
  │ 共有/視聴        ▼
  └────────► LiveKit ノード A / B / C …      ← メディア面。ルームは 1 つのノードにしか載らない
                    ▲
                    │ WHIP（直通、トランスコードなし）
                  OBS
```

**2 つの配信経路は独立しています。** ブラウザの「画面を共有」は Next.js をトークン取得で 1 回だけ通り、
その後は映像がブラウザから **LiveKit に直結**します（`getDisplayMedia` → WebRTC）。Vercel も Ingress も
通りません。OBS の経路はサーバー側で先に ingress を作り、そこへ OBS が WHIP を送ります。だから
「OBS 配信」スイッチは後者だけを閉じます —— オフにしてもブラウザ共有はそのまま使えます。

## UI

独自のデザインシステムで、UI フレームワークへの依存もなく Tailwind も使っていません ——
CSS カスタムプロパティと、薄い React プリミティブの層だけです。

| パス | 役割 |
| --- | --- |
| `src/styles/tokens.css` | すべてのデザイン変数（`--mx-*`）。ライトは `:root`、ダークは `[data-theme="dark"]` |
| `src/styles/base.css` | リセット + タイポグラフィのユーティリティ |
| `src/styles/components.css` | プリミティブのスタイル（ボタン、フォーム、カード、テーブル、モーダル…） |
| `src/styles/shell.css` | アプリの外殻: 上部バー、サイドバー、ステータスバー、言語選択 |
| `src/styles/pages.css` | ページ単位の組み立て: ログインページ、統計タイル、映像ステージ |
| `src/styles/landing.css` | トップページ（`/`）。唯一の対外ページ。後述 |
| `src/ui/` | React プリミティブ。トークンだけを消費し、色やサイズを直書きしない |
| `src/components/AppShell.tsx` | 上部バー + 折りたためるサイドバー + 本文 + ステータスバー。1024px 未満でサイドバーはドロワーに |
| `src/components/LanguageSwitcher.tsx` | 言語のドロップダウン。テーマ切り替えボタンのすぐ左 |
| `src/components/BrandMark.tsx` | ブランドマーク（等角投影の立方体 + 上りの信号）。後述 |
| `src/lib/theme.ts` | テーマの永続化（システム / ライト / ダーク）+ 初回描画のちらつき防止スクリプト |

意図的な 4 つのトレードオフ:

- **テーマは初回描画より前に決める。** `themeBootstrapScript` を `<head>` にインライン展開し、最初の
  描画前に `data-theme` を `<html>` に付けるので、白がちらつくことがありません。
- **テーマは既定でシステムに従う。** 保存されるのは**設定値**（`system` / `light` / `dark`）で、
  解決済みの色を持つのは `<html>` の `data-theme` だけ —— この 2 つを分けないと「システムに従う」を
  表現する場所がなくなります。
- **映像ステージは常にダーク。** `--mx-stage-bg` は両テーマとも黒に近い色です —— 映像の周りが明るいと、
  映像そのものの見え方が変わってしまいます。
- **トップページは独自の文字サイズ段階を持つ。** `landing.css` の冒頭で `--land-*` を少数だけ宣言して
  います（hero の字号、セクションのリズム）。`--mx-font-size-display` は 30px で、ページ見出しには
  ちょうどよく hero には小さすぎるためです。色・角丸・影は今も全部 `--mx-*` を通ります。

### 言語

UI は**简体中文・繁體中文・English・Français・Русский・日本語・Tiếng Việt** の 7 言語で提供されます。
知っておく価値のある 3 つの決定:

- **言語はサーバー側で決める**: `mxds.lang` cookie（ユーザーが明示的に選んだもの）→ `Accept-Language`
  （つまりシステムに従う）→ 最後の砦として英語。サーバー側でなければならない理由は、`<html lang>` と
  最初に描画される文言がすでに正しくないといけないからです。クライアントで `navigator.language` を読むと、
  読み込みごとに違う言語が一瞬ちらつきます。
- **どの文言セットも英語版に対して型チェックされる。** `src/i18n/messages/en.ts` がキーの集合を定義し、
  他の 6 つは `Messages` として宣言されます。したがってキーの抜けや綴り間違いは UI に生のキーを出す
  代わりに `npm run typecheck` で落ちます。差し込みは `{name}`、文中の強調は `**太字**` / `` `コード` ``
  と書いて `<RichText>` が描画します —— こうすればマークアップが文言セットに混ざらず、翻訳者が JSX に
  触る必要もありません。
- **API のエラーメッセージは文章ではなくメッセージキー。** ルートハンドラーは `api.node.duplicate` のような
  キーを投げ、`route()` のラッパー（`src/lib/api-route.ts`）が、そのエラーを引き起こしたリクエストの言語で
  一度だけ翻訳します。zod のバリデーションメッセージも同じで、そのおかげで `src/lib/validation.ts` は
  依存ゼロの純粋なデータモジュールのままです。

言語の選択はテーマ切り替えボタンのすぐ左にあり、アプリ外殻の上部バーとトップページのバーの両方に置いて
います。スマートフォンではトップページのバーがそれを隠します。そこでのバーの役目はマーク、プロジェクト名、
GitHub リンクだからです（後述）。ログインページは隅に独自の選択を持っているので、システム言語が認識され
なかった場合でも行き止まりにはなりません。

### トップページ

`/` はルーターではなく、プロジェクトについて語るページです: 上部バー + hero + 配信経路 + 無料枠の実算 +
機能 + クイックスタート + デスクトップアプリの予告 + Q&A + 締めの CTA。ログイン済みなら CTA は
「コンソールを開く」に、未ログインなら「ログイン / 登録」になります。

**データベースが未設定でも開けなければなりません** —— それがまさに、これを読みたい状況だからです。
そのため `currentUser()` の失敗は飲み込んで未ログイン扱いで描画し（`src/app/page.tsx`）、
トップページまで 500 にはしません。

Q&A は自作のアコーディオンではなくネイティブの `<details>` を使います: このページはサーバーコンポーネント
なので JS 無しでも開かなければならず、キーボード操作とスクリーンリーダーの読み上げはブラウザがすでに
正しくやってくれます。

**上部バーは固定のブレークポイントではなく優先度で項目を落とします。** プロジェクト名はちょうど 23 文字
ですが、「ログイン / 登録」はフランス語だと中国語のほぼ 2 倍の幅になります。つまり固定のブレークポイントは
どこかの言語で早すぎるか遅すぎるかになります。`src/components/LandingBarFit.tsx` は代わりに実測します:
バーが全部を収めきれないとき、テーマ切り替えとログインの CTA が**一緒に**退き、マーク・完全なプロジェクト名・
GitHub リンクが残ることを保証します。デスクトップでは何も落ちません。

デスクトップアプリの節は `MX-Desktop-Sharing-APP`（自前ホスティング、エンドツーエンド暗号化のチャット +
画面共有）の話です。**まだ 1 行も書かれていない**ので、この節は全体を「検討している」「するつもり」の
語調で書き、「構想段階」のバッジを付けています —— トップページで既成事実のように書けば、それは嘘の約束です。
2 つの CTA はどちらもこのリポジトリの issues と discussions に向いています。専用のメールアドレスや
問い合わせフォームはありません。

### ブランドマーク

等角投影の立方体（ルームが紐づく LiveKit ノード）と、その上に持ち上がった折り角（外へ押し出される
ストリーム）です。2 つの形は同じ 2:1 の等角傾斜を共有するので、折り角の 2 本の腕は立方体の上面の稜と
厳密に平行になります。

`src/components/BrandMark.tsx` が唯一の真実の源です。3 つの面の色は `--mx-mark-{top,right,left,signal}`
から取り、テーマごとに定義しています —— 明暗を不透明度で作ると、暗い背景では光の関係が反転してしまいます。
`public/` には独立したファイルもあります: `logo-mark.svg`（明るい背景用）、`logo-mark-dark.svg`、
`logo-tile.svg`（下地つき。favicon / アプリアイコン用）、`logo-glyph.svg`（単色）、
`logo-lockup.svg`（横組み）。


## 認可モデル

トークンに署名する前に必ず `requireMember` を通します。出てくる grant はこうです:

```ts
{ roomJoin: true, room: <そのルームの code>, canSubscribe: true, canPublish: <ロールに応じて> }
```

`room` にはルーム名が 1 つしか入らないので、このトークンで別のルームを購読することは物理的に不可能です。
`roomCreate` / `roomAdmin` / `roomList` は与えません —— ルームはサーバーが作ります。

メンバーを外すには 3 つを同時にやる必要があり、そうしないと外し漏れます（すべて実装済み）: メンバー行を
削除（以後は新しいトークンが署名されない）、`RemoveParticipant`（現在の接続を切る。すでに発行された
トークンは期限まで有効なので）、その人の ingress を削除（そうしないと彼の OBS はルームに送り続けられる）。

「OBS 配信」スイッチも同じ話です —— データベースのフラグを倒すだけでは何も閉じません。あのストリームキーは
LiveKit 側でまだ有効だからです。そこで閉じるとき、このルームの生きている ingress ごとに 2 つを行います:
`DeleteIngress`（リソースを削除して、古いキーでは二度と接続できなくする）と `RemoveParticipant`
（`obs:` の参加者を外して、全員が即座にその映像を受け取らなくする —— DeleteIngress が進行中のセッションも
終わらせるかはドキュメントに書かれておらず、賭ける価値はありません）。続いて行を revoked にし、最後に
フラグを書いて新規作成の要求を止めます。代償は、再び有効にした後で各自が URL を作り直す必要があること:
LiveKit にはキーを保つソフトな停止 `UpdateIngress(enabled=false)` がありますが、JS サーバー SDK の
`updateIngress` は `enabled` を露出していません（固定のフィールド一覧からリクエストを組み直し、それ以外は
捨てます）。使うなら Twirp リクエストを手で組み立てることになります。「オフに見えて実はオフでない」
スイッチを出すより、一度キーを差し替えてもらうほうがましです。

## 無料枠はどれくらい持つか

ユーザーに自分のノードを持たせる理由はこれで全部です。LiveKit Cloud の無料 Build プランは **project**
単位で計量され、超過するとリクエストが素直に失敗して課金は一切されません。しかも同一アカウントの複数の
無料 project は枠を**共有**します:

- WebRTC 参加者分 5,000 分
- 下り帯域 50 GB
- 同時参加者 100、Ingress / Egress は各 2 同時
- トランスコード 60 分（**これがまさに RTMP ではなく WHIP を使う理由** —— RTMP 入力は必ずトランスコード
  されるので、月に 1 時間しか持ちません）

要点: ingress / egress の participant は接続分を**消費しません**。消費するのは視聴者だけです。

視聴者のビットレートで計算すると（下り 50 GB が主なボトルネック）:

| 配信ビットレート | 視聴者 1 分あたりの通信量 | 50 GB で持つ視聴者分 | 視聴者時間に換算 |
| --- | --- | --- | --- |
| 4 Mbps（1080p 高ビットレート） | 30 MB | 1,667 | 約 28 h |
| 2.5 Mbps（1080p 標準） | 18.75 MB | 2,667 | 約 44 h |
| 1.5 Mbps（720p） | 11.25 MB | 4,444 | 約 74 h |
| 0.8 Mbps | 6 MB | 5,000（分の上限に到達） | 約 83 h |

**分水嶺はおよそ 1.33 Mbps**: これより高いと 50 GB の帯域が先に尽き、低いと 5,000 分が先に尽きます。

「実際にどれくらい会議ができるか」に換算すると —— 視聴者時間を視聴者数で割ります:

- 1 人が共有 + 1 人が視聴、1080p: 月あたり約 **44 時間**
- 1 人が共有 + 3 人が視聴、1080p: 月あたり約 **15 時間**
- 1 人が共有 + 9 人が視聴、1080p: 月あたり約 **5 時間**

結論: 単一の無料 project は**試用のための枠であって、製品を運用するための枠ではありません**。だから
このプロジェクトはノードを一級の存在として扱います —— 各ユーザーが自分の LiveKit Cloud project を
接続することで、枠は「サイト管理者の 1 人分」から「めいめい 1 人分」に変わります。内蔵ノードは
あくまで受け皿なので、必ず `maxRooms` を設定してください。

## 既知の制限

- WHIP 直通には**サーバー側 simulcast がありません**。複数層は OBS 32.1.0 以降で自分で有効にする必要が
  あります。
- 自前ホスティングの LiveKit で OBS から配信するには、Ingress + Redis を別途デプロイする必要があります
  （上記の方式 2 参照）。
- 鍵のローテーションツールはありません: `CREDENTIAL_ENCRYPTION_KEY` を差し替えると、保存済みのノード
  認証情報はすべて復号できなくなります。
- 使用量のダッシュボードはありません。上の表から自分で見積もる必要があります。
