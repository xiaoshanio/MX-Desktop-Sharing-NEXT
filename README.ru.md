# MX-Desktop-Sharing-NEXT

Демонстрация рабочего стола на основе LiveKit. Главная идея: **один узел на комнату, один адрес публикации на человека**.

- **Комната привязана к узлу LiveKit.** При создании вы выбираете, какой набор ключей LiveKit использует комната, и именно на этом узле расходуются её медиатрафик и бесплатная квота.
- **Обычные пользователи приносят свой узел.** Каждый подключает свой project в LiveKit Cloud, расходует свою квоту и ни с кем не конкурирует.
- **Встроенный узел как подстраховка.** Администратор может сделать любой узел «встроенным», чтобы им пользовался весь сайт, с переключателями «доступен ли обычным пользователям» и ограничением числа комнат.
- **Авторизация — на уровне протокола.** Нет в таблице участников → нет токена → нет подключения к комнате → нет подписки ни на одну дорожку. Это не фильтрация на клиенте.
- **OBS идёт через WHIP напрямую.** `enableTranscoding: false`, поэтому 60 минут транскодирования в месяц никогда не расходуются.
- **«Публикация из OBS» — настоящий выключатель.** Владелец может закрыть WHIP-вход комнаты одним щелчком: то, что публикуется, обрывается сразу, а все выданные адреса становятся недействительными. Показ из браузера — отдельный путь, его это не касается.
- **Для запуска достаточно двух переменных окружения.** Аккаунт админа создаётся автоматически, ключ шифрования выдаётся автоматически, а LiveKit настраивается в веб-интерфейсе.

О развёртывании сайта на Vercel см. [DEPLOY.md](DEPLOY.md).

## Быстрый старт

Нужны всего две переменные окружения. Скопируйте `.env.example` в `.env.local` (Next **не читает** сам
`.env.example` — правка того файла ни на что не влияет) и заполните эти две:

```bash
DATABASE_URL=postgresql://...@ep-xxx-pooler.../neondb?sslmode=require
ADMIN_PASSWORD=придумайте-свой-пароль
```

**Кавычки необязательны** — с ними и без них результат разбора одинаков. Единственное исключение —
значение с `#`: без кавычек оно молча обрежется как комментарий, так что в этом случае кавычки нужны.
`ADMIN_PASSWORD` должен быть непустым; оставить его как `""` равносильно «не задан», и аккаунт админа
создан не будет.

Затем создайте таблицы и запустите:

```bash
npm install
npm run db:migrate
npm run dev
```

`db:migrate` читает файлы миграций из `drizzle/` и создаёт 12 таблиц. Он читает те же env-файлы, что и
приложение (`.env.local` имеет приоритет над `.env`). **При развёртывании на Vercel запускать это
вручную не нужно** — шаг миграции уже встроен в сборку: настройте `DATABASE_URL` и запушьте код,
подробности в [DEPLOY.md](DEPLOY.md).

Откройте `http://localhost:3000` и войдите как `admin@localhost` с паролем выше —
**аккаунт админа создаётся при первом запуске, мастера установки нет**.

После входа откройте в боковой панели «Узлы LiveKit» → «Подключить узел» и настройте узел LiveKit (как
получить ключи — в следующем разделе). LiveKit не занимает ни одной переменной окружения.

Другие команды: `npm test` (137 проверок), `npm run typecheck`, `npm run build`.
`build` сначала выполняет миграцию базы (пропускается, если `DATABASE_URL` не задан); чтобы собрать, не
трогая базу, используйте `npm run build:only`.

### Вход не работает?

**Сначала откройте `/api/health`** — он по пунктам сообщает состояние каждого этапа, не требует входа и
намного быстрее, чем гадать по стектрейсу.

```bash
curl -s http://localhost:3000/api/health | python -m json.tool
```

Пять пунктов по порядку: задан ли `DATABASE_URL` → доступна ли база → **созданы ли 12 таблиц** → задан ли
`ADMIN_PASSWORD` → прошла ли начальная инициализация. Пока не пройден предыдущий пункт, следующие
пропускаются, поэтому исправлять всегда нужно только самый верхний красный.

Эндпоинт входа разделяет коды статуса по причине:

| Ответ | Значение |
| --- | --- |
| `503 not_configured` | База недоступна, таблиц нет, или `DATABASE_URL` не задан |
| `503 admin_not_configured` | База отвечает, но `ADMIN_PASSWORD` пуст, поэтому аккаунт админа так и не создан |
| `401 invalid_credentials` | Аккаунт существует, пароль неверный |
| `429 rate_limited` | 8 неудач для одного адреса за 15 минут (30 с одного IP) |

Самый легко неверно истолкованный случай: **таблицы не созданы**. Симптом — `database` показывает
«Подключено», но всё, что обращается к таблицам, падает: подключиться и создать таблицы — разные вещи.
Пункт `tables` в `/api/health` прямо перечисляет, каких таблиц не хватает. При развёртывании сборка
создаёт их сама; локально доберите командой `npm run db:migrate`.

Запустили `db:migrate`, а таблиц всё равно нет? Проверьте, существует ли `drizzle/meta/_journal.json`.
Когда drizzle-kit его не находит, он **не выдаёт ошибку** — он тихо создаёт пустой и ничего не делает.
`tests/migrations.test.mts` сторожит именно это. Если всё же попались, `npm run db:push` может обойти
файлы миграций и создать таблицы прямо по `schema.ts`.

### Только для своих (закрыть регистрацию)

**Администрирование → «Настройки сайта» → выключите «Разрешить регистрацию».** Переключатель хранится в
таблице `app_config` (ключ `registration_enabled`), не занимает переменных окружения и действует сразу,
без повторного развёртывания. Когда ключа нет, по умолчанию **открыто** — обновление существующего
развёртывания никогда не оставит людей за дверью неожиданно.

Главное: **создать аккаунт можно тремя путями, и закрыть один — значит закрыть все три**, иначе вы не
закрыли ничего:

| Вход | Поведение после закрытия |
| --- | --- |
| E-mail + пароль | `POST /api/auth/register` сразу отвечает `403 registration_closed` |
| GitHub / Google | Уже связанные аккаунты входят как обычно; тем, кто не связан и чьего адреса здесь тоже нет, отказывают на шаге создания аккаунта |
| Код по e-mail | То же — существующие аккаунты входят как обычно, новые адреса больше не создают аккаунт |

Поэтому проверка не написана на входе трёх маршрутов; она собрана в `assertRegistrationOpen()` в
`src/lib/site-settings.ts` и вызывается **двумя местами, которые действительно вставляют в users** (две
функции resolve в `src/lib/accounts.ts` плюс маршрут register). Внешний вход и вход по коду из письма по
сути означают «войти, если аккаунт есть, иначе создать»; блокировать нужно только вторую половину, а
первая должна продолжать работать.

Два намеренных решения о том, где именно ставить проверку:

- **Путь с кодом из письма блокируется *после* проверки кода, а не *до* отправки.** Эндпоинт отправки
  отвечает одинаково независимо от того, есть адрес в базе или нет (иначе он превратится в эндпоинт для
  перебора пользователей); блокировка на этом шаге уничтожила бы это свойство.
- **В маршруте register блокировка стоит перед проверкой на человека.** Токен Turnstile одноразовый;
  сжечь его на запросе, который заведомо будет отклонён, значит заставить пользователя проходить проверку
  снова только для того, чтобы прочитать «регистрация на этом сайте отключена».

Вкладка «Регистрация» на странице входа при этом исчезает, а вместо неё появляется строка «регистрация на
этом сайте отключена — существующие аккаунты по-прежнему могут входить». Но это лишь подсказка. Если
поменять полученный фронтендом `registrationEnabled` на `true`, серверную проверку это всё равно не
обойдёт.

# Развёртывание узла LiveKit

Сайт не содержит медиасервера. Каждая комната должна быть привязана к узлу LiveKit, а узел может быть из
одного из двух источников.

**Сначала вывод**: почти всем подойдёт первый вариант. Второй стоит выбирать только если у вас уже есть
сервер и вы готовы развернуть вдобавок сервис Ingress.

| | Вариант 1 · LiveKit Cloud | Вариант 2 · Своё размещение |
| --- | --- | --- |
| Время | Около 3 минут | От полудня |
| Стоимость | Бесплатный план Build, без карты | Сервер + трафик |
| Публикация из OBS (Ingress) | **Работает сразу** | **Требует отдельного развёртывания Ingress + Redis** |
| Квота | Жёсткие лимиты (расчёт в конце) | Ограничена только вашим каналом |
| Нужен домен / сертификат | Нет | Да, сертификат от CA; самоподписанный не годится |

## Вариант 1 · LiveKit Cloud (рекомендуется)

### 1. Зарегистрироваться и создать project

Откройте [cloud.livekit.io](https://cloud.livekit.io) и зарегистрируйтесь. Бесплатный план **Build** не
требует карты.

Создайте project с любым названием. После создания вы получите адрес вида `wss://xxx.livekit.cloud` —
это первое из нужных значений.

### 2. Создать API Key

В project откройте **Settings → Keys → создать API Key**, и вы получите:

- `API Key` (вида `APIxxxxxxxx`)
- `API Secret`

> **API Secret показывается один раз.** Закроете диалог — и он потерян навсегда. Скопируйте сразу.
> Потерять не смертельно: удалите этот ключ в консоли LiveKit, создайте новый, вернитесь сюда и
> обновите через «Сменить ключи».

### 3. Подключить к сайту

Войдите → боковая панель **«Узлы LiveKit» → «Подключить узел»** и заполните три значения:

| Поле | Что вводить |
| --- | --- |
| Название узла | Что угодно, оно только для вас |
| Адрес LiveKit | `wss://xxx.livekit.cloud` |
| API Key | Ключ из предыдущего шага |
| API Secret | Секрет из предыдущего шага |

Нажмите «Сохранить». **Сайт по-настоящему обращается к API LiveKit с этими ключами, и неверные никогда
не сохраняются.** Проверка делает две вещи:

- `listRooms` — проверяет, верны ли адрес и ключи. **Неудача отменяет сохранение.**
- `listIngress` — проверяет, можно ли создавать адреса публикации для OBS. **Неудача только понижает
  возможности, но не блокирует** (комната всё равно работает для показа из браузера, просто не выдаст
  WHIP-адрес).

Результат записывается в `capabilities` узла, и каждая строка на странице «Узлы LiveKit» показывает,
доступен ли Ingress. Нажать «Проверить» и перепроверить можно в любой момент.

### 4. Настроить webhook (рекомендуется)

Работает и без него; просто не будет серверных записей о входах и выходах (фронтенд по-прежнему видит
видео и число людей в реальном времени, потому что это события SDK LiveKit, которые от webhook не зависят).

На странице «Узлы LiveKit» под каждым **вашим** узлом показан его собственный адрес webhook вида:

```
https://ваш-сайт/api/webhooks/livekit/<nodeId>
```

Скопируйте его в консоль LiveKit → этот project → **Settings → Webhooks**.

> Почему адрес у каждого узла свой: подпись webhook формируется ключом и секретом отправителя. В схеме с
> несколькими узлами нужно сначала *из URL* понять, какой узел его прислал, и только потом выбрать
> правильный ключ для проверки подписи. Именно для этого в пути есть `nodeId`.

### 5. Проверить, создав комнату

Вернитесь на страницу «Комнаты» и создайте комнату, выбрав только что подключённый узел. Внутри:

- Кнопка «Показать мой экран» → публикует без установки OBS
- Панель «URL публикации OBS» → нажмите «Создать адрес публикации», чтобы получить Server + Bearer Token
- Переключатель «Публикация из OBS» в верхней части той же панели → когда владелец его выключает, комната
  перестаёт принимать потоки WHIP

## Вариант 2 · Своё размещение LiveKit

### ⚠️ Прочитайте это первым, иначе потратите время зря

**Самостоятельно поднятый `livekit-server` не включает Ingress.** Ingress — отдельный сервис, который
общается с livekit-server через Redis. То есть:

- Только **показ экрана из браузера** → Ingress не нужен, достаточно livekit-server
- Хотите **публикацию по OBS/WHIP** → нужно дополнительно развернуть сервис Ingress + Redis и настроить
  `whip_base_url` на стороне livekit-server так, чтобы он указывал на него

Сайт обнаружит недоступный Ingress при проверке и прямо скажет в интерфейсе комнаты, что «адрес публикации
для OBS выдать нельзя».

### Быстрый запуск для локальной разработки

```bash
livekit-server --dev --bind 0.0.0.0
```

Установка: macOS `brew install livekit`; Linux `curl -sSL https://get.livekit.io | bash`;
Windows — скачайте из GitHub Releases.

Режим `--dev` использует фиксированные ключи **`devkey` / `secret`** и подходит только локально. При
подключении к сайту укажите адрес `ws://localhost:7880` (проверка адреса на сайте принимает `ws://`
именно для своего размещения и внутренних сетей).

### Развёртывание в production

Есть официальный генератор конфигурации, с ним намного проще, чем писать конфиг руками:

```bash
docker pull livekit/generate
docker run --rm -it -v$PWD:/output livekit/generate
```

Он создаёт каталог под введённый вами домен, а в нём `docker-compose.yaml`, `livekit.yaml`, `caddy.yaml`,
`redis.conf` и скрипт запуска.

Ключевые пункты `livekit.yaml`:

```yaml
port: 7880
log_level: info
rtc:
  tcp_port: 7881
  port_range_start: 50000
  port_range_end: 60000
  use_external_ip: true      # в облаке определяет настоящий публичный IP через STUN
redis:
  address: redis:6379        # в production настоятельно рекомендуется
keys:
  APIyourkey: your_secret_here   # это просто соответствие key: secret
turn:
  enabled: true
  domain: turn.example.com   # должен совпадать с сертификатом
  tls_port: 443              # используйте 443, когда впереди нет балансировщика
```

`keys:` — действительно просто таблица соответствий; отдельной команды генерации нет — придумайте
достаточно случайный секрет сами:

```bash
openssl rand -base64 32
```

Порты, которые нужно открыть:

| Порт | Протокол | Назначение |
| --- | --- | --- |
| 7880 | TCP | Сигнализация (впереди поставьте терминацию HTTPS/TLS) |
| 7881 | TCP | TCP-резерв для WebRTC-медиа |
| 50000–60000 | UDP | WebRTC-медиа |
| 3478 или 5349 | TCP | Встроенный TURN over TLS (ставьте 443, если нет балансировщика) |
| 443 | UDP | Необязательный TURN/UDP, для пробивания строгих файрволов |
| 6789 | TCP | Необязательные метрики Prometheus |

Две частые ошибки:

- **Нужен сертификат, выданный CA**; самоподписанный не работает. Точка входа выглядит как
  `wss://livekit.example.com`.
- **В Docker используйте host networking**, а не пробрасывайте порты через bridge, иначе диапазон
  медиапортов ломается.

### Развёртывание Ingress (нужно только для публикации из OBS)

- Отдельный сервис; **его адрес Redis должен быть тем же, что использует livekit-server**
- На экземпляр рекомендуется **≥ 4 CPU / 4 ГБ RAM**
- Порты: RTMP `1935/TCP`, WHIP `8080/TCP`, WHIP over UDP `7885/UDP`
- Параметры конфигурации: `api_key`, `api_secret`, `ws_url`, `redis`
  (или переменные окружения `LIVEKIT_API_KEY` / `LIVEKIT_API_SECRET` / `LIVEKIT_WS_URL`)
- **На стороне livekit-server нужно также задать `whip_base_url`** (для RTMP добавьте
  `rtmp_base_url`), иначе сервер не сможет создать адрес ingress
- Для нескольких экземпляров нужен балансировщик: TCP LB для RTMP, HTTP-реверс-прокси для WHIP

Хорошая новость: **WHIP напрямую (bypass transcoding) почти не расходует CPU** — в официальной
формулировке «a WHIP session with transcoding bypassed consumes minimal resources». Сайт по умолчанию
работает именно напрямую (`enableTranscoding: false`), поэтому нагрузка на машину с самостоятельно
поднятым Ingress намного меньше, чем можно подумать. По-настоящему CPU едят RTMP и WHIP с включённым
транскодированием, и это растёт линейно с разрешением и числом слоёв.

## Как заполнять OBS

Получив адрес публикации:

1. OBS → Настройки → Трансляция → **Сервис: `WHIP`**
2. **Server** = Server из панели
3. **Bearer Token** = Bearer Token из панели (так WHIP называет stream key)

Если адрес не создаётся или поток обрывается на ходу, сначала проверьте, не выключил ли владелец
переключатель «Публикация из OBS» в верхней части панели.

У WHIP напрямую нет серверного simulcast. Для нескольких уровней качества включите его сами в
**OBS 32.1.0+** (поддерживается 1–4 слоя).

## Частые вопросы по подключению узлов

| Симптом | Причина / что делать |
| --- | --- |
| Адрес введён как `https://` | Менять не нужно; сайт сам превратит его в `wss://`, а также срежет лишний путь и завершающий слеш |
| При сохранении пишет «не удаётся подключиться либо ключи неверны» | Проба `listRooms` не прошла. Проверьте, что адрес относится к этому project, что key/secret — парные, и что секрет скопирован полностью |
| Ingress показывает «—» / недоступен | Cloud: в project не включён Ingress, либо исчерпана его конкурентность (на бесплатном уровне их всего 2). Своё размещение: Ingress не развёрнут, либо не задан `whip_base_url` |
| Эти ключи уже подключены | Один и тот же пользователь + тот же адрес + тот же key можно подключить только один раз; найдите существующую запись в списке |
| Все запросы внезапно падают | Бесплатная квота исчерпана. **Превышение приводит к отказу и никогда не тарифицируется** — дождитесь следующего месяца или смените узел |
| Секрет потерян | Пересоздайте key в консоли LiveKit, вернитесь сюда и обновите через «Сменить ключи» (новые ключи проверяются до записи) |

## Архитектура

```
Браузер ──── Next.js on Vercel ──── Neon Postgres
  │          (вход / комнаты / участники / подпись токенов)
  │                 │
  │ WebRTC          │ server SDK (ключами того узла, к которому привязана комната)
  │ показ/просмотр  ▼
  └────────► Узел LiveKit A / B / C …        ← медиаплоскость; комната живёт ровно на одном узле
                    ▲
                    │ WHIP (напрямую, без транскодирования)
                  OBS
```

**Два пути публикации независимы.** Браузерное «Показать мой экран» проходит через Next.js один раз — за
токеном, после чего видео **идёт прямо в LiveKit** (`getDisplayMedia` → WebRTC), не касаясь ни Vercel, ни
Ingress; путь OBS требует, чтобы сервер сначала создал ingress, и уже потом OBS отправляет WHIP в
LiveKit. Поэтому переключатель «Публикация из OBS» закрывает только второй — выключите его, и показ из
браузера продолжит работать.

| Путь | Назначение |
| --- | --- |
| `src/db/schema.ts` | 12 таблиц. `livekit_nodes` — сердце всей архитектуры |
| `src/lib/livekit.ts` | Узел → SDK-клиент, подпись токенов, создание WHIP-ingress, проверка ключей |

| `src/lib/site-settings.ts` | Политика уровня сайта (сейчас только «разрешить регистрацию»), включая охрану создания аккаунтов |

## Интерфейс

Собственная дизайн-система, без зависимости от UI-фреймворка и без Tailwind —
только CSS-переменные плюс тонкий слой React-примитивов.

| Путь | Назначение |
| --- | --- |
| `src/styles/tokens.css` | Все переменные дизайна (`--mx-*`). Светлая тема живёт на `:root`, тёмная на `[data-theme="dark"]` |
| `src/styles/base.css` | Сброс + типографические утилиты |
| `src/styles/components.css` | Стили примитивов (кнопки, формы, карточки, таблицы, модальные окна…) |
| `src/styles/shell.css` | Оболочка приложения: верхняя панель, боковая панель, строка состояния, выбор языка |
| `src/styles/pages.css` | Композиции уровня страницы: страница входа, плитки статистики, видеосцена |
| `src/styles/landing.css` | Главная страница (`/`). Единственная страница «наружу», см. ниже |
| `src/ui/` | React-примитивы; они потребляют только токены и никогда не пишут цвет или размер напрямую |
| `src/components/AppShell.tsx` | Верхняя панель + складываемая боковая + основная область + строка состояния; ниже 1024px боковая превращается в выдвижную |
| `src/components/LanguageSwitcher.tsx` | Выпадающий список языков, сразу слева от переключателя темы |
| `src/components/BrandMark.tsx` | Знак бренда (изометрический куб + восходящий сигнал), см. ниже |
| `src/lib/theme.ts` | Хранение темы (система / светлая / тёмная) + скрипт против мигания при первой отрисовке |

Четыре осознанных компромисса:

- **Тема определяется до первой отрисовки.** `themeBootstrapScript` встроен в `<head>` и ставит
  `data-theme` на `<html>` раньше любой отрисовки, поэтому вспышки белого не бывает.
- **По умолчанию тема следует за системой.** В хранилище лежит *предпочтение*
  (`system` / `light` / `dark`), и только `data-theme` на `<html>` содержит разрешённый цвет — эти два
  понятия должны быть разделены, иначе «следовать за системой» негде выразить.
- **Видеосцена всегда тёмная.** `--mx-stage-bg` почти чёрный в обеих темах — светлая рамка вокруг видео
  меняет то, как читается само видео.
- **У главной страницы своя типографическая шкала.** `landing.css` объявляет сверху небольшой набор
  `--land-*` (размеры hero, ритм секций), потому что `--mx-font-size-display` — это 30px: в самый раз для
  заголовка страницы и слишком мало для hero. Цвет, радиус и тень по-прежнему идут через `--mx-*`.

### Языки

Интерфейс поставляется на **упрощённом китайском, традиционном китайском, английском, французском,
русском, японском и вьетнамском**. Три решения, о которых стоит знать:

- **Язык определяется на сервере**: cookie `mxds.lang` (явный выбор) → `Accept-Language` (то есть
  «следовать за системой») → английский как запасной. Именно на сервере, потому что `<html lang>` и
  первый отрисованный кадр уже должны быть правильными: чтение `navigator.language` на клиенте давало бы
  вспышку не того языка при каждой загрузке.
- **Каждый набор строк проверяется типами против английского.** `src/i18n/messages/en.ts` задаёт набор
  ключей; остальные шесть объявлены как `Messages`, поэтому пропущенный или опечатанный ключ ломает
  `npm run typecheck`, а не показывает сырой ключ в интерфейсе. Подстановки записываются как `{name}`;
  выделения внутри текста пишутся как `**жирный**` / `` `код` `` и отрисовываются `<RichText>` — так
  разметка не попадает в наборы строк, и переводчику не нужно трогать JSX.
- **Сообщения об ошибках API — это ключи, а не готовый текст.** Обработчики маршрутов бросают ключи вида
  `api.node.duplicate`, а обёртка `route()` (`src/lib/api-route.ts`) переводит один раз — на языке того
  запроса, который вызвал ошибку. То же и с сообщениями валидации zod, поэтому `src/lib/validation.ts`
  остаётся чистым модулем данных без зависимостей.

Выбор языка стоит сразу слева от переключателя темы — и в верхней панели оболочки, и в панели главной
страницы. На телефоне панель главной страницы его скрывает: там её задача — знак, название проекта и
ссылка на GitHub (см. ниже), а страница входа держит собственный переключатель в углу, чтобы нераспознанный
системный язык никогда не оказался тупиком.

### Главная страница

`/` — это страница о проекте, а не маршрутизатор: верхняя панель + hero + пути публикации + честный
расчёт бесплатной квоты + возможности + быстрый старт + анонс настольного приложения + вопросы и ответы +
финальный призыв. Когда вы вошли, призыв меняется на «Открыть консоль»; иначе — «Вход / Регистрация».

**Она обязана открываться даже когда база не настроена** — именно тогда её и нужно читать больше всего.
Поэтому ошибка `currentUser()` проглатывается и страница рисуется как для неавторизованного
(`src/app/page.tsx`), а не отдаёт 500 вместе со всем остальным.

Вопросы и ответы используют нативный `<details>`, а не самодельный аккордеон: страница — серверный
компонент, она должна раскрываться без JS, а клавиатуру и экранные читалки браузер уже делает правильно.

**Верхняя панель убирает элементы по приоритету, а не на фиксированной точке перелома.** Название проекта —
ровно 23 символа, но «Вход / Регистрация» по-французски почти в два раза шире, чем по-китайски, так что
любая жёстко заданная точка перелома срезала бы слишком рано или слишком поздно в каких-то языках.
`src/components/LandingBarFit.tsx` вместо этого измеряет: когда панель не может вместить всё, переключатель
темы и кнопка входа уходят **вместе**, что гарантирует сохранение знака, полного названия проекта и ссылки
на GitHub. На компьютере не убирается ничего и никогда.

Раздел про настольное приложение — о `MX-Desktop-Sharing-APP` (самостоятельно размещаемый мессенджер со
сквозным шифрованием + демонстрация экрана). **Не написано ни строки**, поэтому весь этот раздел
сформулирован через «рассматриваем» и «планируем» и помечен значком «стадия идеи» — написать это как
свершившийся факт на главной странице было бы просто ложным обещанием. Оба призыва ведут в issues и
discussions этого репозитория; отдельного адреса почты или формы обратной связи у проекта нет.

### Знак бренда

Изометрический куб (тот узел LiveKit, к которому привязана комната) с приподнятым сверху уголком (поток,

## Модель авторизации

Перед подписью токена обязательно проходит `requireMember`. Получающийся grant таков:

```ts
{ roomJoin: true, room: <код этой комнаты>, canSubscribe: true, canPublish: <по роли> }
```

В `room` помещается только одно имя комнаты, поэтому этот токен физически нельзя использовать для
подписки на другую комнату. Он не даёт ни `roomCreate`, ни `roomAdmin`, ни `roomList` — комнаты создаёт
сервер.

Удаление участника требует трёх действий сразу, иначе оно «протекает» (всё реализовано): удалить строку
участника (новый токен больше не подпишется), `RemoveParticipant` (оборвать текущее соединение, потому что
уже выданный токен действует до истечения срока) и удалить его ingress (иначе его OBS сможет продолжать
публиковать в комнату).

С переключателем «Публикация из OBS» та же история — перевернуть флаг в базе не закрывает ничего, потому
что этот stream key на стороне LiveKit всё ещё действителен. Поэтому при закрытии с каждым живым ingress
комнаты происходят две вещи: `DeleteIngress` (удалить ресурс, чтобы старый ключ больше не подключился) и
`RemoveParticipant` (выкинуть участника `obs:`, чтобы все немедленно перестали получать его видео — в
документации не сказано, завершает ли DeleteIngress уже идущую сессию, и ставить на это не стоит); затем
строка помечается отозванной, и наконец пишется флаг, блокирующий новые запросы на создание. Цена в том,
что после повторного включения каждому придётся создать новый адрес: у LiveKit есть мягкое закрытие с
сохранением ключа, `UpdateIngress(enabled=false)`, но `updateIngress` в серверном JS SDK не выставляет
`enabled` (он пересобирает запрос по фиксированному списку полей и выбрасывает всё лишнее), так что
пользоваться им пришлось бы, собирая Twirp-запрос вручную. Лучше заставить один раз сменить ключ, чем
выпустить переключатель, который «выглядит выключенным, но не выключен».

## На сколько хватает бесплатной квоты

В этом и состоит вся причина, по которой пользователи приносят свой узел. Бесплатный план Build в LiveKit
Cloud считается по **project**; при превышении запросы просто не проходят и никогда не тарифицируются, а
несколько бесплатных projects под одним аккаунтом **делят** одну квоту:

- 5 000 минут-участников WebRTC
- 50 ГБ исходящего трафика
- 100 одновременных участников, по 2 одновременных Ingress / Egress
- 60 минут транскодирования (**именно поэтому WHIP, а не RTMP** — вход по RTMP всегда транскодируется, а
  это всего час в месяц)

Ключевой момент: участники ingress / egress **не считаются** в минутах подключения, поэтому расходуют их
только зрители.

Расчёт по битрейту зрителя (50 ГБ исходящего трафика — основное узкое место):

| Битрейт публикации | Трафик на минуту-зрителя | Минут-зрителей на 50 ГБ | В зрительских часах |
| --- | --- | --- | --- |
| 4 Мбит/с (1080p, высокий битрейт) | 30 МБ | 1 667 | ≈ 28 ч |
| 2,5 Мбит/с (1080p, обычный) | 18,75 МБ | 2 667 | ≈ 44 ч |
| 1,5 Мбит/с (720p) | 11,25 МБ | 4 444 | ≈ 74 ч |
| 0,8 Мбит/с | 6 МБ | 5 000 (упирается в лимит минут) | ≈ 83 ч |

**Примерно 1,33 Мбит/с — водораздел**: выше него первыми заканчиваются 50 ГБ трафика, ниже — 5 000 минут.

В переводе на «сколько реально можно провести встреч» — зрительские часы делятся на число зрителей:

- 1 показывает + 1 смотрит, 1080p: около **44 часов в месяц**
- 1 показывает + 3 смотрят, 1080p: около **15 часов в месяц**
- 1 показывает + 9 смотрят, 1080p: около **5 часов в месяц**

Вывод: один бесплатный project — это **квота на пробу, а не квота на продукт**. Поэтому в этом проекте
узлы сделаны полноправной сущностью: каждый пользователь подключает свой project в LiveKit Cloud, и квота
превращается из «одной на владельца сайта» в «по одной на каждого». Встроенный узел нужен лишь как
подстраховка, так что обязательно задайте ему `maxRooms`.

## Известные ограничения

- У WHIP напрямую **нет серверного simulcast**; несколько слоёв нужно включать самому в OBS 32.1.0+.
- Публикация из OBS при своём размещении LiveKit требует отдельного развёртывания Ingress + Redis (см.
  вариант два выше).
- Инструмента ротации ключа нет: как только `CREDENTIAL_ENCRYPTION_KEY` заменена, все сохранённые ключи
  узлов становятся нерасшифровываемыми.
- Панели с расходом квоты нет; придётся оценивать по таблице выше.
